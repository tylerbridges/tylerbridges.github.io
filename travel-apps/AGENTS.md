# AGENTS.md — Travel Apps

Rules for any coding agent (Codex, Claude Code) working in this folder.

## What this is
Two static web apps split out of Tyler's Travel Dashboard (a Claude artifact). The dashboard is separate and is not in this repo; never try to change it from here.
- `packing-list/` — packing checklist built from Tyler's preferences (`preferences.js`).
- `itinerary-generator/` — day-by-day itinerary from trip dates, flights and lodging.
- `shared/` — helpers, local storage (`store.js`), optional Claude adapter (`ai.js`), shell (`shell.js`), styles.

No build step, no dependencies, no framework. Plain ES5-style browser JS loaded with `<script>` tags in a fixed order (see each `index.html`). All paths are relative, so the folder works at the repo root or in a subfolder on GitHub Pages.

## Rules
- Packing List is now a generator: setup → rule-based generation → review → native Notes export. Notes owns packing/check-off; do not reintroduce in-app packing meters or packed/unpacked filters into the main flow. `generator.js` and `generator.css` own this standalone flow; preserve the extracted `packing.js` functions for compatibility. The itinerary app retains its existing flow through optional `APP` hooks in the shared shell.
- The active packing MVP uses `refinement-engine.js` (pure rule groups with dependency declarations), `refinement-state.js` (versioned inputs, assumptions, overrides and a preserved baseline), and `refinement-ui.js` (compact setup and semantic refinements). Keep item identity separate from label and quantity. Refinements rerun affected rules; explicit overrides survive. Legacy items remain pinned until explicitly returned to automatic. Preserve the older generator functions for compatibility.
- `trip/<ID>/pack_meta/refinement` is the structured source for new lists; the existing section/item documents remain the export adapter. Keep profile exclusions in `meta/packing.refinementProfile`, inspectable and resettable. Do not silently learn or remove critical/required items. Local learning in `learning.js` stores exported opportunities and explicit post-trip feedback in `meta/packingLearning`. Only explicitly reviewed items count, once per trip; comparable context gates last-five suggestions. Never treat generation/removal as actual-use feedback or silently apply suggestions. Separate automatic preparation observations in packingLearning.editTrips from explicitly reviewed actual-use reports. Observe final saved additions/removals/edits once per trip; Undo replaces evidence. Four matching edits among five comparable opportunities, or three additions among five, yield visible suggestions. Only safe usual-item exclusions can be approved; protect critical/required items and clothing. Contrary contexts block blanket exclusions. Keep automatic history inspectable, pausable/resettable; forgetting a trip prevents observing it again. Reset pauses observation and preserves applied defaults. Critical/required items, clothing, manual items and Snacks cannot be excluded through learning. Apply safe shared-profile exclusions only after explicit confirmation, and keep history/reset separate from applied-default reset. No live forecasts.
- Preserve existing `meta/packing` preferences and trip records. Dates are required for new generation. A separate `trip/<ID>/pack_meta/draft` holds review edits; exported lists retain the established `pack_sections` / `pack_items` shapes. Keep user-selected weather distinct from live forecasts, and keep deterministic rules independent of API keys.
- ENEX native Notes checklists were confirmed by Tyler's device screenshot. Keep the title in the ENEX title field only, section headings in the body, and one `en-todo` element per item.
- The repo is the source of truth; read the current files before editing.
- Make incremental edits. Don't restructure or regenerate whole files unless asked.
- `packing.js` and `itinerary.js` are extracted from the dashboard. Keep their structure and function names so future dashboard changes can be ported; mark standalone-only changes with a `Standalone app:` comment.
- Keep data shapes compatible with the dashboard: `trips/<ID>` (with `bookings` map), `trip/<ID>/pack_sections`, `trip/<ID>/pack_items`, `trip/<ID>/pack_meta/original`, `trip/<ID>/itinerary/main`, `meta/packing`, `templates/<id>`.
- Never commit an API key or any secret. The Claude key is entered in the app's Settings and lives only in the browser.
- Mobile first: works at 360–430px wide, inputs at 16px (no iPhone zoom), light and dark mode.
- Bump the `?v=N` cache-bust query on every changed script/stylesheet in the `index.html` files.
- Itinerary rules (from the dashboard): local times, no "~" on times, realistic arrival times, every flight gets its ground legs (MSP: leave home 3½ hr before, at MSP 2 hr before; elsewhere head to the airport 2½ hr before; after landing get to lodging or head home to Rochester), lodging line only on the check-in day with "N nights", Maps links never carry an origin (the page adds the day's start at display time).
- Tyler's confirmed refinement preferences: no Pack lighter (old settings normalize to Standard); usual accessories stay included except opt-in trip extras: Kindle, Hotspot, Belkin charging pad, Garmin + charger (paired) and extra phone case. Expose these in setup Trip extras and the Extras refinement, off by default; preserve pinned overrides. All other reviewed usual items remain automatic. T-shirts daily, bottoms every two days; Pack extra adds one T-shirt, two underwear, two pairs of socks and one pair of bottoms. Laundry uses first wash + interval plus one spare clothing day. Cool/cold trips keep hoodie and puffer even with “I run hot.” Carry-on only warns about space conflicts; never moves layers or reduces quantities. Workouts assumes most days, uses regular clothing, and requires enough shorts for two days per pair even in cool weather; preserve manual shortfalls with warnings. Ordinary hikes use Brooks; rugged/wet-trails toggle adds hiking footwear. Daypack is opt-in via I need a daypack in setup/Activities; neither usual extras nor hiking automatically add it. Optional setup weather defaults to unconfirmed. Preserve manual overrides, automatically remove unedited items no longer required, and explain profile-exclusion exceptions for required items.
- Guided wardrobe decisions: suit days, video-call workdays and nice dinners are distinct. Work needs a fresh long-sleeve top per video day, not dedicated bottoms. Full suit days and video-call workdays default to zero, including restored blank drafts, without clearing entered positive counts. Trip type and work equipment changes must not blank zero workdays; reused styles start workday counts at zero. Dinner tops include polo, short-sleeve nice shirt, long-sleeve nice shirt, button-up and named Other. Only button-ups share work shirts; other dinner tops remain fresh and separate. Dinner bottoms include shorts/jeans/khakis and named Other with an explicit belt choice; reuse matching bottoms. Custom outfit IDs stay stable across label changes and their names/belt flag enter rule and review fingerprints. Jeans/khakis/suit share one belt. One reusable suit jacket/trousers/dress shoes; fresh white dress shirts and dress socks per suit day, no undershirts. Ties and alternate-with-khakis default on for new lists: one each for one suit day, two different ties and two pairs of khakis for multiple suit days, shared with dinners. Preserve existing explicit opt-outs; confirm choices in the suit step. Suit shirts default separate; compatibility may enable sharing. Assume maximum work/dinner (and compatible suit) shirt overlap, but show and permit corrections. Nice shirt counts never reduce for laundry. Laundry and Pack extra use one buffer total; preserve the extra when no laundry buffer was actually included. Weather means coldest expected outdoor conditions; allow warmer-weather shorts separately. Show quantity impact during outfit decisions and sharing alternatives; after confirmation, show export controls inline on the same page as outfit quantities and warnings; do not open another export sheet. ENEX is always the primary/default export on all devices, even with an older saved format preference; keep formatted copy and Markdown below under More export options. Using an alternative must not promote it to the default; label ENEX as Mac import and explain direct iPhone import is unsupported. Preserve native ENEX contents. Keep alternatives/preview under More export options. After generation, centralize assumptions in Trip plan summary cards; each opens its focused editor. Mark outstanding outfit choices in the overview and outfit editor. Remove repeated optional review/checklist controls; do not replay confirmed questions. Required conditional decisions use context fingerprints, reopen when inputs change, cannot be skipped in the guided flow, and must be resolved before export. Generation remains quick with visible provisional assumptions. Preserve the current setup/calendar and optional general-refinement flow; never reset explicit item overrides.
- Toiletries split into Dry toiletries and Liquid toiletries in generation, preferences and exports; keep IDs/quantities and explicit section overrides. Assume solid deodorant/lip balm; item editing can adjust bag assignment. Do not add a liquids-bag item or liquids-specific departure check. One general Toiletries packed? check covers both sections. Do not move personal-bag items automatically. Preserve manual legacy items.
- Packing rules: one item per line, one definite quantity (socks/underwear 2 per travel day, T-shirts 1 per day, shorts/pants days÷2 rounded up, contacts 5 × ceil((days+2)/5)); Before leaving is one-to-one with the list (wallet, ID and bags always; never Global Entry/PreCheck or boarding-pass checks).

- `app-update.js` compares local asset versions against uncached HTML on launch/resume and once per visible minute. Reload idle views into a fresh URL; show Load update while a form/sheet is open and preserve drafts. Do not reload a failed autosave. No remote API or dependency is required.
- `autosave.js` stores unfinished setup/refinement/item/preference/style/feedback form drafts under `meta/packingFormDrafts/<scope>`. Save immediately on edits, restore matching-context drafts with a visible notice, allow discard, and clear only after a successful confirmed save. Never apply drafts directly to rules/profile/learning evidence. Keep calendar dates and structured preference/feedback edits resumable, respect test namespaces, and show storage failures.
- First-use custom onboarding remains design-only until forced Tyler-specific contributions become profile-aware. Separate person/profile setup from per-trip setup; preserve legacy Tyler behavior and overrides, and fingerprint personal policy in rule caches and learning. Do not expose choices the current engine cannot honor.
- Quick setup has one Outfit needs toggle for occasion counts and equipment; the trip-type dropdown is retired from the UI. Preserve saved trip types internally and infer the type for new trips without a selected style. Save count confirmation fingerprints so export does not repeat them. `trip-styles.js` reuses selected high-level inputs and refinements only: never dates, destination, weather, occasion counts, outfit decisions or manual overrides. Built-in/custom styles are optional; show carried laundry assumptions and require fresh relevant counts.

- Embedded Test flow uses `?test=1` with `packing-test:` storage isolation. Named scenario configurations survive resets; resets clear only sandbox `ta:` documents. Configurable previews show engine quantities; fixed checks remain separate. Active-test validation must bypass caches for fresh comparisons, display manual overrides separately, and retain warnings. Capture refined variants with an explicit manual-edits choice; preserve full work equipment. Reject invalid counts visibly, keep copy names distinct, and retain the selected saved variant. Scenario checks run fixed regression cases in memory with visible expected/actual values; never mutate the saved test while checking. Both direct reads/writes and Store documents must use the same namespace; never clear real data during test reset. Reuse production setup/refinement/export UI.
